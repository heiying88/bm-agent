# 技能创建器

一个用于创建新技能并对其迭代改进的技能。

从整体上看，创建一个技能的流程大致如下：

- 确定你希望这个技能做什么，以及大致要怎么做
- 写出技能草稿
- 创建几个测试提示词，并运行 claude-with-access-to-the-skill（能访问该技能的 claude）来执行
- 帮助用户从定性和定量两个角度评估结果
  - 趁运行在后台进行时，如果还没有定量 eval，就先起草一些（如果已有，可以直接沿用，或在你觉得有必要调整时修改）。然后向用户解释这些 eval（如果原本就存在，就解释现有的那些）
  - 使用 `eval-viewer/generate_review.py` 脚本把结果展示给用户查看，同时也让他们看到定量指标
- 根据用户对结果的评估反馈重写技能（如果定量基准暴露出明显缺陷，也一并处理）
- 重复以上过程，直到满意为止
- 扩充测试集，再以更大规模重试

使用这个技能时，你的职责是判断用户正处于流程的哪一步，然后切入并帮助他们推进各个阶段。举例来说，用户可能说"我想做一个处理 X 的技能"。你可以帮忙厘清他们的确切意图、写草稿、编写测试用例、确定他们想要的评估方式、运行全部提示词，然后循环往复。

反过来，用户也可能已经有了技能草稿。这种情况下，你可以直接进入循环中评估/迭代的部分。

当然，你始终应该保持灵活。如果用户说"我不需要跑一堆评估，跟我凭感觉来就行"，那就照他们的方式来。

等技能完成之后（不过再说一次，顺序是灵活的），你还可以运行技能描述优化器——我们为它准备了一整套独立的脚本——来优化技能的触发。

明白了吧？明白。

## 与用户沟通

技能创建器的用户群体，对编程术语的熟悉程度可能千差万别。如果你还没听说过（你怎么可能听说过，这股风潮最近才刚开始）：如今 Claude 的强大能力正在激励水管工们打开终端，让父母和祖父母辈去搜索"how to install npm"。另一方面，大多数用户大概都具备不错的计算机素养。

所以，请注意语境线索，据此把握沟通的措辞！默认情况下，给你一个大致的参考：

- "evaluation"（评估）和 "benchmark"（基准测试）属于边界地带的术语，但可以接受
- 对于 "JSON" 和 "assertion"（断言），要先看到用户确实懂这些概念的明确信号，再不加解释地使用

拿不准时简单解释一下术语是完全可以的；如果不确定用户能否理解某个术语，尽管用一句简短的定义把它说清楚。

## 创建技能

### 捕捉意图

先从理解用户的意图开始。当前对话里可能已经包含了用户想要沉淀成技能的工作流（比如他们说"把这个变成一个技能"）。如果是这种情况，先从对话历史中提取答案——用过的工具、步骤的先后顺序、用户做过的修正、观察到的输入/输出格式。缺失的部分可能需要用户补齐，并且进入下一步之前应先让用户确认。

1. 这个技能应该让 Claude 能做什么？
2. 这个技能应该在什么时候触发？（用户的哪些措辞/场景）
3. 期望的输出格式是什么？
4. 要不要建立测试用例来验证技能是否有效？输出可以客观验证的技能（文件转换、数据提取、代码生成、固定的工作流步骤）能从测试用例中受益。输出偏主观的技能（写作风格、艺术创作）通常不需要。根据技能类型给出合适的默认建议，但由用户决定。

### 访谈与调研

主动询问边界情况、输入/输出格式、示例文件、成功标准和依赖项。把这部分彻底理清之前，先不要写测试提示词。

查看可用的 MCP——如果对调研有帮助（搜索文档、寻找类似技能、查阅最佳实践），在条件允许时通过子代理并行调研，否则就内联进行。提前备好上下文，减轻用户的负担。

### 编写 SKILL.md

根据用户访谈的结果，填写以下组成部分：

- **name**：技能标识符
- **description**：何时触发、做什么。这是主要的触发机制——既要写明技能做什么，也要写清什么时候该用它的具体场景。所有"何时使用"的信息都应放在这里，而不是正文里。注意：目前 Claude 有"触发不足"（undertrigger）的倾向——技能明明能派上用场却不使用。为了对治这一点，请把技能描述写得稍微"主动"一点。比如，与其写"如何构建一个简单快速的仪表盘来展示内部 Anthropic 数据"，不如写成"如何构建一个简单快速的仪表盘来展示内部 Anthropic 数据。只要用户提到仪表盘、数据可视化、内部指标，或想展示任何类型的公司数据，即使没有明确说出"仪表盘"二字，也务必使用这个技能。"
- **compatibility**：所需工具、依赖项（可选，很少需要）
- **技能的其余部分 :)**

### 技能编写指南

#### 技能的解剖结构

```
skill-name/
├── SKILL.md（必需）
│   ├── YAML frontmatter（name、description 必填）
│   └── Markdown 指令
└── 捆绑资源（可选）
    ├── scripts/    - 用于确定性/重复性任务的可执行代码
    ├── references/ - 按需加载进上下文的文档
    └── assets/     - 输出中使用的文件（模板、图标、字体）
```

#### 渐进式披露

技能采用三级加载体系：
1. **元数据**（name + description）—— 始终在上下文中（约 100 词）
2. **SKILL.md 正文** —— 技能触发时进入上下文（理想情况下少于 500 行）
3. **捆绑资源** —— 按需使用（不限量，脚本无需加载即可执行）

这些字数只是约数，需要更长时尽管加长。

**关键模式：**
- 把 SKILL.md 控制在 500 行以内；如果接近这个上限，就增加一层层级结构，并清楚指明使用该技能的模型接下来该去哪里继续深入。
- 在 SKILL.md 中清晰地引用各个文件，并说明何时该读取它们
- 对于大型参考文件（>300 行），附上目录

**按领域组织**：当一个技能支持多个领域/框架时，按变体组织：
```
cloud-deploy/
├── SKILL.md（工作流 + 选择逻辑）
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```
Claude 只读取相关的参考文件。

#### 无惊扰原则

这自不必说：技能不得包含恶意软件、漏洞利用代码或任何可能危害系统安全的内容。技能的内容意图若向用户描述，不应让用户感到意外。不要配合创建具有误导性的技能，或用于实施未授权访问、数据外泄等恶意活动的技能。不过像"扮演某个 XYZ 角色"这类技能是没有问题的。

#### 编写模式

指令编写优先使用祈使句。

**定义输出格式**——可以这样写：
```markdown
## Report structure
ALWAYS use this exact template:
# [Title]
## Executive summary
## Key findings
## Recommendations
```

**示例模式**——附上示例很有用。可以这样编排（不过如果示例中出现了 "Input" 和 "Output" 字样，可以适当变通）：
```markdown
## Commit message format
**Example 1:**
Input: Added user authentication with JWT tokens
Output: feat(auth): implement JWT-based authentication
```

### 写作风格

尽量向模型解释事情为什么重要，以此代替生硬老套的 MUST 说教。运用心智推演（theory of mind），尽量让技能保持通用，而不是极度局限于特定示例。先写出一版草稿，再以新鲜的眼光重新审视并改进。

### 测试用例

写完技能草稿后，构思 2-3 个贴近真实的测试提示词——要像真实用户真的会说出口的那种。把它们分享给用户：[不必一字不差地照搬这段话]"我想试运行这几个测试用例。它们看起来对吗，还是你想再补充一些？"然后运行。

把测试用例保存到 `evals/evals.json`。暂时不要写断言——只写提示词。断言会在下一步运行进行期间起草。

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's task prompt",
      "expected_output": "Description of expected result",
      "files": []
    }
  ]
}
```

完整 schema（包括你稍后会添加的 `assertions` 字段）见 `references/schemas.md`。

## 运行并评估测试用例

本节是一个连续的流程——不要中途停下。切勿使用 `/skill-test` 或任何其他测试技能。

把结果放在 `<skill-name>-workspace/` 中，与技能目录同级。在 workspace 内，按迭代组织结果（`iteration-1/`、`iteration-2/` 等）；每个迭代内部，每个测试用例各占一个目录（`eval-0/`、`eval-1/` 等）。不要预先把整套目录建好——边做边建即可。

### 第 1 步：在同一轮次中启动全部运行（with-skill 与 baseline）

对每个测试用例，都在同一轮次中启动两个子代理——一个带技能，一个不带。这一点很重要：不要先启动 with-skill 运行、之后再回来补 baseline。所有运行一次性全部启动，让它们大约同时完成。

**With-skill 运行：**

```
Execute this task:
- Skill path: <path-to-skill>
- Task: <eval prompt>
- Input files: <eval files if any, or "none">
- Save outputs to: <workspace>/iteration-<N>/eval-<ID>/with_skill/outputs/
- Outputs to save: <what the user cares about — e.g., "the .docx file", "the final CSV">
```

**Baseline 运行**（提示词相同，但 baseline 取决于具体情形）：
- **创建新技能**：完全不带技能。同一提示词，不给技能路径，保存到 `without_skill/outputs/`。
- **改进现有技能**：旧版本。编辑之前，先为技能做快照（`cp -r <skill-path> <workspace>/skill-snapshot/`），再让 baseline 子代理指向该快照。保存到 `old_skill/outputs/`。

为每个测试用例写一个 `eval_metadata.json`（断言暂时可以留空）。根据每个 eval 测试的内容给它起一个描述性的名字——不要只叫 "eval-0"。目录也用这个名字。如果本次迭代使用了新的或修改过的 eval 提示词，要为每个新的 eval 目录创建这些文件——不要想当然地认为它们会从之前的迭代沿用。

```json
{
  "eval_id": 0,
  "eval_name": "descriptive-name-here",
  "prompt": "The user's task prompt",
  "assertions": []
}
```

### 第 2 步：运行进行期间，起草断言

不要干等运行结束——可以把这段时间用起来。为每个测试用例起草定量断言，并向用户解释。如果 `evals/evals.json` 中已有断言，就审查它们，并说明它们各自检查什么。

好的断言应可客观验证，并拥有描述性的名字——它们在基准查看器中要一目了然，让人扫一眼结果就能立刻明白每条断言检查的是什么。偏主观的技能（写作风格、设计质量）更适合定性评估——不要硬给需要人工判断的东西套上断言。

断言起草好后，用它们更新各个 `eval_metadata.json` 文件和 `evals/evals.json`。同时向用户说明他们将在查看器中看到什么——定性输出和定量基准都有。

### 第 3 步：运行陆续完成时，记录耗时数据

每个子代理任务完成时，你会收到一条包含 `total_tokens` 和 `duration_ms` 的通知。立即将这些数据保存到该运行目录下的 `timing.json`：

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

这是捕获这些数据的唯一机会——它们只随任务通知而来，不会在别处持久化。通知到达时就逐条处理，不要攒起来批量处理。

### 第 4 步：评分、汇总并启动查看器

全部运行结束后：

1. **为每个运行评分**——启动一个评分子代理（或内联评分），让它阅读 `agents/grader.md` 并对照输出逐条评估断言。结果保存到每个运行目录下的 `grading.json`。grading.json 的 expectations 数组必须使用 `text`、`passed` 和 `evidence` 字段（不能用 `name`/`met`/`details` 或其他变体）——查看器依赖这些确切的字段名。对于可以用程序检查的断言，编写并运行脚本，而不是靠肉眼——脚本更快、更可靠，还能跨迭代复用。

2. **汇总为基准结果**——在 skill-creator 目录下运行汇总脚本：
   ```bash
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name>
   ```
   它会生成 `benchmark.json` 和 `benchmark.md`，包含每种配置的 pass_rate、时间和 token，附均值 ± 标准差以及差值（delta）。如果需要手动生成 benchmark.json，查看器所要求的确切 schema 见 `references/schemas.md`。
   把每个 with_skill 版本放在对应 baseline 版本之前。

3. **做一轮分析**——阅读基准数据，找出汇总统计可能掩盖的规律。该关注什么，参见 `agents/analyzer.md`（"Analyzing Benchmark Results" 一节）——比如无论技能如何都始终通过的断言（无区分力）、方差偏高的 eval（可能不稳定），以及时间/token 之间的取舍。

4. **启动查看器**，定性输出和定量数据一起带上：
   ```bash
   nohup python <skill-creator-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     > /dev/null 2>&1 &
   VIEWER_PID=$!
   ```
   从第 2 次迭代起，还要传入 `--previous-workspace <workspace>/iteration-<N-1>`。

   **Cowork / 无头环境**：如果 `webbrowser.open()` 不可用或环境没有显示器，改用 `--static <output_path>` 写出一个独立 HTML 文件，而不是启动服务器。用户点击"提交全部评审"时，反馈会以 `feedback.json` 文件的形式下载。下载后，把 `feedback.json` 复制到 workspace 目录，供下一次迭代读取。

注意：请使用 generate_review.py 创建查看器；没有必要手写自定义 HTML。

5. **告知用户**，大意如下："我已在你的浏览器中打开结果。里面有两个标签页——"输出结果"让你逐个点开测试用例并留下反馈，"基准测试"展示定量对比。看完后回到这里告诉我一声。"

### 用户在查看器中会看到什么

"输出结果"标签页每次展示一个测试用例：
- **提示词**：下达的任务
- **输出**：技能产出的文件，尽可能内嵌呈现
- **上一轮输出**（第 2 次迭代起）：折叠区域，展示上一轮迭代的输出
- **正式评分**（若已运行评分）：折叠区域，展示各断言的通过与失败
- **你的反馈**：一个随输入自动保存的文本框
- **上一轮反馈**（第 2 次迭代起）：用户上次的评语，显示在文本框下方

"基准测试"标签页展示统计摘要：每种配置的通过率、耗时和 token 用量，并附每个 eval 的细分数据与分析观察。

通过"上一条/下一条"按钮或方向键导航。看完后，用户点击"提交全部评审"，所有反馈即保存到 `feedback.json`。

### 第 5 步：读取反馈

用户告诉你他们看完后，读取 `feedback.json`：

```json
{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

空的反馈意味着用户觉得没问题。把改进集中在用户明确提出意见的测试用例上。

查看器用完之后，关闭其服务器：

```bash
kill $VIEWER_PID 2>/dev/null
```

## 改进技能

这是整个循环的核心。你已经跑完测试用例，用户也评审过结果，现在需要根据他们的反馈把技能做得更好。

### 如何思考改进

1. **从反馈中归纳泛化。**这里的大图景是：我们试图创造的是能在许多不同提示词上被使用上百万次（也许真是字面意义上的百万，甚至更多，谁知道呢）的技能。而此刻你和用户只在寥寥几个示例上反复迭代，因为这有助于加快速度。用户对这些示例了如指掌，评估新输出对他们来说很快。但如果你们共同打磨的技能只对这几个示例有效，它就没有用。与其塞进琐碎的过拟合式改动，或压抑束缚的 MUST 条款，遇到顽固问题时，你不妨换个思路：试试不同的比喻，或推荐不同的工作模式。尝试成本相对低廉，说不定就能碰出很棒的东西。

2. **保持提示词精炼。**删掉没有发挥作用的内容。务必阅读运行记录（transcript），而不只是最终输出——如果技能似乎在让模型浪费大量时间做无用功，可以试着删掉技能中导致这种行为的部分，看看会发生什么。

3. **解释"为什么"。**尽力解释你要求模型做的每件事背后的**为什么**。如今的 LLM *很聪明*。它们有不错的心智推演能力，配上合适的脚手架就能超越死板的指令，真正把事情做成。哪怕用户的反馈简短甚至带着情绪，也要真正去理解任务本身、用户为什么写下这些话、以及他们实际写了什么，然后把这些理解传递到指令里。如果你发现自己在写全大写的 ALWAYS 或 NEVER，或搭出超级僵硬的结构，那就是一个警示信号——如有可能，换个方式表述并讲清缘由，让模型明白你要求的事情为什么重要。这是一种更人性化、更有力、也更有效的做法。

4. **寻找跨测试用例的重复劳动。**阅读测试运行的记录，留意各子代理是否都不约而同地写了相似的辅助脚本，或对同一件事采取了相同的多步骤做法。如果全部 3 个测试用例都导致子代理去写 `create_docx.py` 或 `build_chart.py`，这就是一个强信号：技能应该捆绑该脚本。写好一次，放进 `scripts/`，并指示技能使用它。这让未来的每次调用都不必再重复造轮子。

这项任务相当重要（我们可是想在这里每年创造数十亿的经济价值！），你的思考时间并不是瓶颈；慢慢来，认真琢磨。建议先写一版修改稿，然后以崭新的眼光重新审视并加以改进。真正尽最大努力走进用户的头脑，理解他们想要什么、需要什么。

### 迭代循环

改进技能之后：

1. 把你的改进应用到技能上
2. 将所有测试用例重新运行到新的 `iteration-<N+1>/` 目录中，包括 baseline 运行。如果是在创建新技能，baseline 始终是 `without_skill`（无技能）——这一点在各迭代间保持不变。如果是在改进现有技能，请自行判断哪种 baseline 更合理：用户带来的最初版本，还是上一次迭代。
3. 启动评审查看器，让 `--previous-workspace` 指向上一次迭代
4. 等待用户评审并告诉你他们完成了
5. 读取新的反馈，再次改进，重复

持续进行，直到：
- 用户表示满意
- 反馈全部为空（一切看起来都不错）
- 你没有取得有意义的进展

## 进阶：盲测对比

在需要对一个技能的两个版本做更严格比较的场合（例如用户问"新版本真的更好吗？"），我们有一套盲测对比系统。细节请阅读 `agents/comparator.md` 和 `agents/analyzer.md`。基本思路是：把两份输出交给一个独立的代理，不告诉它哪份是哪份，让它评判质量，然后分析获胜者为何获胜。

这是可选项，需要子代理，大多数用户用不到。人工评审循环通常已经足够。

## 描述优化

SKILL.md frontmatter 中的 description 字段是决定 Claude 是否调用一个技能的首要机制。创建或改进技能之后，可以主动提出优化 description，以获得更好的触发准确率。

### 第 1 步：生成 trigger eval 查询

创建 20 条 eval 查询——should-trigger 与 should-not-trigger 混合。保存为 JSON：

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

这些查询必须真实，是 Claude Code 或 Claude.ai 用户确实会输入的内容。不要抽象的请求，而要具体、明确、带足细节的请求。例如：文件路径、关于用户工作或处境的个人背景、列名和列值、公司名称、URL，再来一点前情铺垫。有些可以全小写，或包含缩写、错别字、口语化表达。长短混合搭配，并侧重边界情况而非一目了然的案例（用户之后会有机会确认它们）。

反面示例：`"Format this data"`、`"Extract text from PDF"`、`"Create a chart"`

正面示例：`"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

对于 **should-trigger** 查询（8-10 条），要考虑覆盖面。同一意图要用不同的措辞表达——有的正式，有的随意。要包含用户没有明确点名技能或文件类型、但显然需要它的情形。再掺入一些不常见的用例，以及该技能与其他技能存在竞争、但应当胜出的情形。

对于 **should-not-trigger** 查询（8-10 条），最有价值的是那些"差一点就中"的近似查询——与技能共享关键词或概念、但实际需要的是别的东西。想想相邻领域、朴素关键词匹配会误触发但不应触发的模糊表述，以及查询涉及技能所做之事、但在那个上下文中另一个工具更合适的情形。

关键要避免的一点：不要把 should-not-trigger 查询做得明显不相关。拿"Write a fibonacci function"当 PDF 技能的反例太容易了——它什么也检验不出来。反例应当真正具有迷惑性。

### 第 2 步：请用户审阅

使用 HTML 模板把评估集呈现给用户审阅：

1. 从 `assets/eval_review.html` 读取模板
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → eval 条目组成的 JSON 数组（外面不要加引号——这是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能名称
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的描述
3. 写入一个临时文件（如 `/tmp/eval_review_<skill-name>.html`）并打开：`open /tmp/eval_review_<skill-name>.html`
4. 用户可以编辑查询、切换 should-trigger、增删条目，然后点击"导出评估集"
5. 文件会下载到 `~/Downloads/eval_set.json`——如果下载文件夹里存在多个版本（例如 `eval_set (1).json`），请认准最新的那个

这一步很重要——糟糕的 eval 查询会导致糟糕的描述。

### 第 3 步：运行优化循环

告诉用户："这会需要一些时间——我会在后台运行优化循环，并定期回来查看进度。"

把评估集保存到 workspace，然后在后台运行：

```bash
python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --verbose
```

使用你系统提示词中的模型 ID（即驱动当前会话的那个模型），这样触发测试才能与用户的真实体验一致。

运行期间，定期查看输出尾部，向用户汇报当前进行到第几轮迭代、分数如何。

它会自动完成整个优化循环：把评估集拆成 60% 训练集和 40% 留出测试集，评估当前描述（每条查询运行 3 次以获得可靠的触发率），然后调用 Claude 根据失败项提出改进。每个新描述都会在训练集和测试集上重新评估，最多迭代 5 次。完成后，它会在浏览器中打开一份 HTML 报告，逐轮展示结果，并返回含有 `best_description` 的 JSON——按测试集分数而非训练集分数选定，以避免过拟合。

### 技能触发的工作原理

理解触发机制有助于设计更好的 eval 查询。技能以"名称 + 描述"的形式出现在 Claude 的 `available_skills` 列表中，Claude 根据描述决定是否查阅某个技能。需要知道的重要一点是：Claude 只会在自己无法轻松独立完成的任务上查阅技能——像"读取这个 PDF"这样简单的一步式查询，即使描述完美匹配也可能不触发技能，因为 Claude 用基础工具就能直接处理。而复杂、多步骤或专业性的查询，只要描述匹配就能可靠地触发技能。

这意味着你的 eval 查询应该有足够的实质内容，让 Claude 确实能从查阅技能中受益。"读取文件 X"这类简单查询是糟糕的测试用例——无论描述质量如何，它们都不会触发技能。

### 第 4 步：应用结果

从 JSON 输出中取出 `best_description`，更新技能的 SKILL.md frontmatter。向用户展示修改前后的对比，并报告分数。

### 打包并交付（仅在 `present_files` 工具可用时）

检查你是否可以使用 `present_files` 工具。如果没有，跳过这一步。如果有，打包技能并把 .skill 文件呈现给用户：

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

打包完成后，把生成的 `.skill` 文件路径告诉用户，方便他们安装。

## Claude.ai 专属说明

在 Claude.ai 中，核心工作流是一样的（草稿 → 测试 → 评审 → 改进 → 重复），但由于 Claude.ai 没有子代理，部分机制需要调整。需要适配的内容如下：

**运行测试用例**：没有子代理就意味着无法并行执行。对每个测试用例，先阅读技能的 SKILL.md，然后按其指令亲自完成测试提示词。一次只做一个。这不如独立子代理严格（技能是你写的、又由你来运行，你握有全部上下文），但作为一次健全性检查很有用——而且人工评审环节可以弥补。跳过 baseline 运行——直接按要求用技能完成任务即可。

**评审结果**：如果无法打开浏览器（例如 Claude.ai 的虚拟机没有显示器，或你在远程服务器上），就完全跳过浏览器评审器，改为直接在对话中展示结果。对每个测试用例，展示提示词和输出。如果输出是用户需要查看的文件（如 .docx 或 .xlsx），把它保存到文件系统并告知位置，让他们下载检查。在对话中直接征求反馈："这个看起来怎么样？有什么想改的吗？"

**基准测试**：跳过定量基准测试——它依赖 baseline 对比，而没有子代理时这种对比没有意义。专注于用户的定性反馈。

**迭代循环**：与之前相同——改进技能、重跑测试用例、征求反馈——只是中间没有浏览器评审器。如果环境里有文件系统，仍然可以把结果组织到各个迭代目录中。

**描述优化**：这一部分需要 `claude` CLI 工具（具体是 `claude -p`），它只在 Claude Code 中可用。在 Claude.ai 上请跳过。

**盲测对比**：需要子代理。跳过。

**打包**：`package_skill.py` 脚本只要在有 Python 和文件系统的地方就能运行。在 Claude.ai 上，你可以运行它，用户可以下载生成的 `.skill` 文件。

**更新现有技能**：用户也可能是想让你更新现有技能，而不是创建新技能。这种情况下：
- **保留原始名称。**记下技能的目录名和 frontmatter 中的 `name` 字段——原样使用。例如，已安装的技能是 `research-helper`，就输出 `research-helper.skill`（而不是 `research-helper-v2`）。
- **编辑前先复制到可写位置。**已安装技能的路径可能是只读的。复制到 `/tmp/skill-name/`，在那里编辑，并从副本打包。
- **如果手动打包，先在 `/tmp/` 中暂存**，再复制到输出目录——直接写入可能因权限问题失败。

## Cowork 专属说明

如果你在 Cowork 中，主要需要知道这些：

- 你有子代理，所以主工作流（并行启动测试用例、运行 baseline、评分等）都可用。（不过，如果遇到严重的超时问题，把测试提示词改成串行运行也是可以的。）
- 你没有浏览器或显示器，所以生成 eval 查看器时，使用 `--static <output_path>` 写出一个独立的 HTML 文件，而不是启动服务器。然后提供一个链接，用户点击后即可在他们的浏览器中打开该 HTML。
- 不知出于什么原因，Cowork 环境似乎会让 Claude 在跑完测试后不太愿意生成 eval 查看器，所以再重申一遍：无论你在 Cowork 还是 Claude Code 中，跑完测试后，都应该始终先为人类生成 eval 查看器、让他们查看示例，然后你再自己去修改技能、尝试纠正——查看器要用 `generate_review.py` 生成（不要自己手写独家定制的 HTML 代码）。先说声抱歉，接下来我要用全大写喊一句：*先生成 EVAL 查看器，再由你自己去评估输入*。要尽快让人类看到这些结果！
- 反馈的流转方式不同：由于没有运行中的服务器，查看器的"提交全部评审"按钮会把 `feedback.json` 以下载文件的形式保存。之后你可以从那里读取（可能需要先申请访问权限）。
- 打包可用——`package_skill.py` 只需要 Python 和文件系统。
- 描述优化（`run_loop.py` / `run_eval.py`）在 Cowork 中应该完全可用，因为它通过 subprocess 调用 `claude -p`，不依赖浏览器；但请等到技能彻底完成、且用户认可它的状态之后再进行。
- **更新现有技能**：用户也可能是想让你更新现有技能，而不是创建新技能。请遵循上文 claude.ai 一节中的更新指引。
